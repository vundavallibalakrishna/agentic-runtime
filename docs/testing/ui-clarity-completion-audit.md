## Remaining conditions for full-goal proof

1. A legitimate writable preview origin is required for real form saves, generation and positive workflow verification. Existing real requests from the separate UI are refused with `csrf_failed`; the review retains this response and does not alter or spoof security settings. This same limitation was independently observed in suite settings and run setup before the completion refresh.
2. The owning existing list contracts need server-side bounded pagination/search/filtering before 100,000-record end-to-end scale can be called working. UI slicing, fixture-based component stress and small actual tenant lists are insufficient. Reuse the existing endpoints/repositories and regenerate clients in a separately authorised backend stage.
3. Actual configured guest/pack/widget/signing and other data-dependent flows require their legitimate records/contracts and positive access. The core guest guide is an accurate unavailable-address state, not the pack content implementation. OQ-161 and the other scoped open questions retain their owning follow-ups; UI work does not repair or certify those services.

The deployment check exposes only non-secret settings: AR_ENV is staging, AR_PUBLIC_URL is http://127.0.0.1:3000 and AR_CSRF_ALLOWED_ORIGINS is empty. `CsrfMiddleware` in `services/api/src/ar_api/middleware/stack.py` uses those settings; `auth/csrf.py:origin_ok` keeps exact host/port matching outside dev/ci. No setting was changed. Branch scope was checked from merge base a1319771c7c0ec8950c87d7bcc0ace1274a6431b: 181 committed files across 134 commits were under apps/web or docs before the final guest/audit stage; none were outside those directories.

These are substantive evidence gaps against the full goal, not optional polish. Expanding into backend implementation, changing deployment security/origin policy, or inserting synthetic customer data would exceed the owner's current constraint. The UI changes can be reviewed live on 3102 while these boundaries remain explicit.
